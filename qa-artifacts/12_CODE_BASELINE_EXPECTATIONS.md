## Inputs That Code Cannot Supply

Release owners, not QA observation, must provide actual site-specific target values where acceptance depends on them: approved fleet/workload and latency targets; RPO/RTO and maintenance allowance; data-class retention/legal-hold and recoverability policy; exact supported player hardware, OS/browser/accessibility matrix; and real site network exposure/egress policy. The current code behavior above is the starting characterization for all other topics. If product owners choose a different rule, record that decision against its BQ/BR ID before scoring acceptance. QA should leave actual behavior blank until execution; no human is being asked to rediscover source behavior.

## Packet 3 Code Baseline

- Backup health uses immutable execution outcomes for latest verified success, failed runs for latest failure, and active `backup_runs` attempt/heartbeat/lease fields; it does not infer a success from the latest row.
- Downloads are limited to DATABASE/OBJECTS/CONFIGURATION `.age` artifacts from signature-trusted committed local V2 publications after fresh unconditional Backup/download authorization and audit. Legacy sources remain explicitly unsupported.
- Recovery reports enter through a deployment command as signed canonical projections with increasing per-site sequence. CMS reads only the release-03 table and has no recovery execution endpoint.
- Metrics and alerts use no run/operation/path/key labels. These are source expectations; live stream, Prometheus and operator-browser evidence is pending.
