# Test Data And Environment Requirements

`QA5` in the case CSV means an isolated five-role replica: Data (PostgreSQL/MinIO), Valkey, Backend API plus worker, CMS, and Observability, with one or more separate physical or virtual player machines. It must be isolated from production identity, storage, network and recovery destinations. The user's previous VM sizes were Data 2 vCPU/5120 MB/50 GB; Backend 3 vCPU/4608 MB/30 GB; CMS 1 vCPU/1536 MB/15 GB; Valkey 2 vCPU/2048 MB/12 GB; Observability 1 vCPU/2048 MB/25 GB. These are reported specifications, not a measured capacity certificate or proof of available disk.

The 2026-10-15 targeted run used a smaller disposable single-host Linux topology with loopback CMS/API/Electron and isolated PostgreSQL/Valkey/RustFS containers. Its exact scope and cleanup boundary are recorded in `evidence/runtime-2026-10-15/runtime-validation.md`. That topology is valid evidence only for the named feature scenarios; it is not the required QA5 release environment or target-hardware matrix.

In the isolated database only, replace one pending account's placeholder hash with a known synthetic password to prove correct-password login is still denied, and retain a synthetic legacy pending session to verify immediate denial. Include a direct-created account as a no-invitation control. Use an authorized manager browser and a second manager account to check that the one-time link appears only in the creation result, is not emailed by the app or returned in lists, and can be delivered through a QA-approved secure channel. Replace a lost and an expired pending link, then try both old and new tokens; include cross-department/read-only managers and activation/disable/delete/replacement races. Test public activation without a prior cookie/CSRF token on the disposable API. Never use or record real invite links or passwords; redact fixture tokens from screenshots/logs. BQ-023/024 are confirmed; separately verify authorized password reset still returns its generated password.
- Department integrity: use only a disposable PostgreSQL database. Seed valid, `NULL` and orphaned `users.department_id` states before migration `0048`; record the fail-closed orphan count/sample and transaction rollback, repair the orphan explicitly, then apply the migration. Afterward test direct invalid assignment, referenced-Department deletion, nullable unassignment and both API race commit orders. Never manufacture an orphan in production.
- Deleted-user fixtures: one tombstoned creator in A, one creator transferred A -> B before deletion, one inactive but not deleted account, and one missing legacy creator. Retain synthetic names and historical references; use a known original email solely to verify scrub/non-disclosure/reuse.
- Custom roles: one with conditional `update Screen` plus matching `create/manage DevicePairing` for selected records, one pairing-only role without Screen update, one Screen-update role whose pairing condition does not match, one with `manage Emergency`, one department-bound content creator, one read-only role, one with independent Schedule action grants, one inherited/conditional User grant and one with no relevant grant. Rename custom roles during testing without changing permissions.
- Paired devices: active landscape, portrait, overlapping-group, revoked/recovered and offline candidates. Use disposable device certificates and test CA.
- Chat actors: owner, moderator, member, removed member and private DM outsider.

Use distinct accounts and browser profiles for concurrent sessions. ## Environment Controls

- For bounded **developer verification** on the 6.2 GiB workstation, run one phase at a time with native Docker and Docker Desktop stopped. Begin a phase only with at least **2.7 GiB MemAvailable** and **1.2 GiB free swap**; stop the active phase below **1.5 GiB MemAvailable** or **1 GiB free swap**. Apply cgroup/Docker memory limits and `NODE_OPTIONS=--max-old-space-size=768` where applicable. These limits replace the impractical earlier 4 GiB local launch gate only for serial developer checks; they do not weaken QA5 or performance acceptance.

- Treat the 2026-10-16 workstation OOM as an execution constraint, not a product result. Kernel evidence shows three `chrome-headless` processes launched inside the VS Code user scope were killed at approximately 2.4 GiB, 2.84 GiB and 2.91 GiB resident memory; VS Code then stopped with the same OOM scope. QA should use a larger representative host and record its own approved guardrails.
- Run resource-heavy phases sequentially: database/services and API checks first; one Playwright browser worker second; close it and verify process exit; Electron/player third; and the combined soak only after moving it to an approved host with adequate measured headroom. Never overlap Playwright/Chromium with Electron on this workstation.
- Constrain Node-based build/test commands with `NODE_OPTIONS=--max-old-space-size=768` unless a recorded test requirement proves that insufficient. Configure Playwright with one worker and no fully-parallel projects for the workstation run. A test retry must reuse the same controlled sequence rather than starting another browser concurrently.
- Record `MemAvailable`, swap usage and the largest resident processes before and after each phase. Do not start any bounded phase below 2.7 GiB available or 1.2 GiB free swap; stop below 1.5 GiB available or 1 GiB free swap, when a configured process/container memory cap is reached, or when sustained growth has no explained plateau. These workstation guardrails prevent another host OOM; they are not product capacity acceptance limits.
- After each browser/player phase, prove that no `chrome-headless`, Playwright, Chromium, Electron, Vite, API or worker process from the run remains. Keep unrelated user and non-DARSHAN services out of cleanup scope; never terminate them merely to satisfy the test harness.
- Keep synchronized clocks and record server, browser and player timezones. BQ-014 reporting-day choice remains TBD; the test fixture must expose both UTC and site-local boundaries.
- Provide test PKI for CMS, Backend, MinIO, PostgreSQL, Valkey, player identity and signed roles. Include a wrong CA/expired certificate set for negative cases.
- Provide controllable network rules to isolate Valkey, WSS, backend, MinIO or off-host backup independently. Record actual firewall source/port rules for BQ-019.
- Use disposable PostgreSQL/MinIO/S3 targets for migrations, backup, restore, low disk and archive tests. The isolated recovery VM must reject nonempty/production targets.
- Run Packet 1 coordination against real disposable PostgreSQL and pg-boss with at least two API/worker processes. Do not use a shared/default coordination key between parallel fixtures. Preserve row/job snapshots around commit, restart, lease expiry, recurring reconciliation and terminal deletion. A mock queue or single-process lock check is not enough for `CONC-08`/`BKP-08..10`.
- For local repository tests use a disposable Linux mount namespace. Record decimal device ID, uid/gid, mode and free bytes before each case; prove the API container has no mount. Under confirmed BQ-027, characterize the worker's current write access and verify the deployed narrow helper/OS policy prevents arbitrary host/key/retention authority; the intended host authority alone owns protected publication/retention paths. Do not point the fixture at `/`, a home directory, production storage or any valued backup. Packet 1+2 success means coordinated raw capture/seal; Packet 3 developer success means worker/helper-client and encryption/publication primitives, not working production automation, retention or restore.
- Keep the age private recovery identity and all signing private keys outside application containers and VMs under test. Inject only public recipient/verifier material to the worker. Test rotation/revocation with disposable keys and preserve public keys needed to verify retained generations.
- Provide a deployment-staged, versioned all-role configuration capsule fixture rather than letting the Backend worker read secrets across VMs. The expected logical paths, maximum bytes, ownership, modes and hashes must be part of the test contract; no production secret may appear in logs, screenshots or this repository.
- If whole-Backend-host or site loss is in scope, provide an independently administered encrypted destination/failure domain and test loss of the local repository. Otherwise record the narrower Data-service-loss promise explicitly; do not mark disaster recovery complete from a same-host copy.
- For abort tests provide a child whose direct parent exits while a grandchild ignores SIGTERM, plus controllable stalled MinIO and retained legacy off-host requests. After deadline/cancellation, inspect process groups, sockets, execution lock, scratch and partial objects. Never use uncontrolled network endpoints.
- Build a pre-0045 legacy copy containing all ownership backfill classes: administrator creator, valid department creator, creator transferred before migration, creator without department, creator pointing at a removed/invalid department where the fixture can safely represent it, missing/nullable creator, and all four resource tables. Capture IDs/counts/checksums before migration. Because legacy rows lack creation-time owner columns, explicitly review the migration-time mapping for transferred creators. Never test the rollback guard by enabling physical deletion against valued data.
- Provide deterministic database barriers and fault controls for deletion versus session checks, socket reconnect, notification insert, multipart activation/finalization and legacy finalization. Provide an S3-compatible target where abort/delete/copy can fail independently, then recover it and replay the cleanup worker.
- Run the document count backfill without `--apply` first, archive its JSON result, compare counts manually, then use `--apply` only on the disposable migrated database. Include a failed object and prove it is reported rather than force-updated.
- Supply real Windows x64 and Ubuntu user-session player hardware with approved portrait/landscape/multi-display fixtures; X11 and Wayland where the site requires them. Browser matrix and accessibility tools are BQ-016 inputs.
- Capture logs, metrics, screenshots, request/response redactions, DB row counts, object hashes, queue/backup manifests, certificate subjects and video of physical display transitions as case evidence. Never include bearer tokens, private keys or real credentials.
- Seed realistic data volume for capacity work only after BQ-017 workload and capacity evidence are approved. Back up disposable state before destructive fault/recovery scenarios and clean test objects afterward.
