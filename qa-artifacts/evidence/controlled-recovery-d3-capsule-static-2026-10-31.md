# D3 capsule static provider packet

This packet implements static reusable capsule providers while live admission remains blocked. **No Docker command, installed source/data command, live SQL/S3 connection, source seed, real age encryption, backup, restore, service stop, host installation or commit occurred.** All generation in verification used disposable temporary test roots. Retained live source services/resources, UI credentials, age key/public receipt history, journals, database and object store were neither inspected nor mutated by this packet. Earlier live observations remain historical evidence rather than new acceptance.

## Implemented contract

- New `controlled-recovery-d3-capsule-{profile,files,crypto,material,render}.ts`, `controlled-recovery-d3-capsule.ts` and `controlled-recovery-d3-age-staging.ts` provide the exact production inventory, pinned template rendering, protected retained material, signed policy/receipt and shared encrypted staging transaction. The foundation factory exposes these concrete components; installed capsule construction remains fail-closed.
- The separate strict capsule profile/schema pins **21 actual checked-in inputs**: five fixed disposable role env templates, production assembly render blocks for CMS/metrics/Grafana, and shared observability configurations/templates/six dashboards. No `.example`, fictional image, production key or host age authority is introduced. No production loader/validator or native recovery behavior is changed.
- Capsule construction requires current exact source stages/resources/layout, no pending role/stop receipt, real protected intent/schema/seal receipts and fresh read-only data-status verification with the seed writer revoked. It checks source/data profile, schema/0057, ledger/content/physical identity bindings, public age receipt and template identities. Preconditions are re-observed after acquiring the supplied operation/controller lock. Missing real seeded receipts fail before capsule effects; unit receipts and fake clients are never installed authority. The source journal is not advanced to `CAPSULE_READY` in this static packet.
- The canonical production five-role allowlist has **61 files plus the embedded manifest signing private key**. `validateProductionCapsuleInventory()` remains the validator. Under approved design B, `source_mode` is the actual stat mode of separate capsule copies: canonical 0640/0644/0600 beneath owned 0700 role roots. Original source/private generation/journal files stay 0600 and the general protected helper is unchanged. Copy publication explicitly applies/verifies the canonical mode before writing under umask077. Stable owner/device/inode/single-link/no-symlink/bounds and exact tree/content checks apply. USTAR metadata uses the separate canonical restore modes, root UID/GID, regular files, sorted paths and mtime 0.
- The archived backend env is self-contained mapped configuration without a `backend.json` selector. Exactly the three accepted derived overlay values are omitted from its base, then published separately after signing, avoiding a hash cycle. Service file credentials, source transport TLS/HBA and Valkey ACL/TLS/persistence/memory declarations bind to retained source inputs. Monitoring credentials/accounts and observability/exporter/runtime configurations are **configuration only**; no monitoring SQL user, exporter, application or restore runtime is started or accepted.
- Policy, manifest and release signing keys are distinct retained disposable Ed25519 PKCS8 authorities, verified with the production canonical key parsers/keyring and policy signer/verifier. Only the manifest private key is embedded at its exact production path. The release authority signs a domain-specific capsule receipt, not a fabricated production release. Fixed enrolled OpenSSL generates a disposable device CA plus backend/CMS/observability EC P-256 certificates, with exact identity/SAN/serial/key-match/chain/expiry/algorithm checks. Server signing reads the retained source CA without copying it or mutating serial files. Private age identity stays outside all capsule inventory/archive paths.
- The concrete reusable shared transaction acquires the exact existing D4 age slot before plaintext publication and retains it across joined recipient/encrypt/decrypt, byte roundtrip/hash validation, exclusive durable ciphertext/publication receipt, exact plaintext cleanup and release. Fixed tool argv, clean environment/no shell/stdin, caps, image/config and exact container settlement remain unchanged. Shared inner invocations remove only their component cidfile; they cannot release the outer owner. Ordinary settled failures clean exact owned staging; uncertainty preserves/quarantines owner/files and forbids reuse. Proven restart recovery requires a dead original PID/start identity, matching owner/settled bindings and no component cidfile, then re-verifies exact cipher/staging content. Matching pre-link and link-before-unlink publication windows recover without reencryption; conflicting owners/content remain blocked.
- Read-only status uses existing protected files and read-only source/data observers, with no lock, generation, publication recovery, pending cleanup, Docker/age invocation or filesystem mutation. Pending/extra/unsafe files, hardlink windows, changed key/receipt/template/source/role/ciphertext/signature bindings reject untouched. Native crypto settlement uncertainty preserves the durable construction owner/marker and prevents retry reuse of pending paths.
