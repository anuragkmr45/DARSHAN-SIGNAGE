# Deleted-User Ownership Source Review

Review date: 2026-10-16  
Source baseline: historical ownership implementation; latest authorization behavior is reconciled through `8f66d8f` in `authorization-session-requests-review.md`.
Evidence type: source inspection, compilation/unit tests, and a partial disposable API/CMS developer run. The run covered the role/scope matrix, stable ownership across transfer/deletion, tombstones, email reuse/history privacy, department conflicts and two CMS screenshots. **Migration `0045`, deterministic races, sockets, final browser coverage and the final frozen build were not runtime-verified.** See `runtime-2026-10-16/runtime-validation.md`.

## Intended Product Behavior

Deleting a CMS user is an account-access operation, not a content-transfer operation. The account becomes a retained tombstone: its stable ID and historical display name remain, its email and credentials are scrubbed, all sessions are revoked, live user sockets are disconnected, and the account cannot sign in or be reactivated. Existing Media, Layout, Presentation, and Schedule records retain their original `created_by` attribution and their independently stored operational owner.

Ownership is assigned at creation and is not recalculated when the creator later changes department or is deleted:

- `ADMIN`-created content is `ORGANIZATION` owned;
- `SUPER_ADMIN`-created content is `RESTRICTED`;
- a department-bound creator's content is `DEPARTMENT` owned by that department;
- legacy content without a valid owner mapping is `RESTRICTED` and administrator-only;
- ownership is never automatically reassigned to another individual;
- published snapshots/player payloads do not contain this control-plane metadata and are not rewritten on account deletion.

Authorization requires both the relevant CASL ability and the stable ownership rule. A global subject manager can manage all applicable scopes. Organization content is readable by permitted users but globally managed. Department Media/Layout/Presentation is readable within its department but mutable only by the creator or global manager. Schedule is the explicit exception: a permitted same-department actor may perform only its granted lifecycle action. Restricted content requires global subject management.

## Source Evidence

### Schema and migration

- `darshan-server/src/db/schema.ts` adds `users.deleted_at` and `users.deleted_by`, retains creator foreign keys, and adds checked/indexed `owner_scope` and `owner_department_id` columns to Media, Layout, Presentation, and Schedule.
- `darshan-server/drizzle/migrations/0045_deleted_user_content_ownership.sql` backfills organization, department, or restricted ownership; adds ownership checks, department `ON DELETE RESTRICT` foreign keys, creator references, and lookup indexes.
- The backfill checks that the creator's department still exists before assigning `DEPARTMENT`; an invalid/missing mapping remains `RESTRICTED` rather than becoming globally readable.
- Legacy rows did not store creation-time ownership, so migration `0045` can use only the creator's role and valid department **at migration time**. It cannot reconstruct a pre-migration department transfer that is absent from durable history. QA/release owners must review that mapping on the disposable copy; stable original-department semantics begin once the new columns are populated.

### Tombstone and immediate access withdrawal

- `darshan-server/src/db/repositories/user.ts::tombstone` locks the user, aborts unfinished uploads, fails associated `PENDING` and `PROCESSING` Media, removes every session, scrubs credentials/email, marks the tombstone, and inserts `USER_DELETED` audit history in one transaction.
- `darshan-server/src/routes/users.ts` preserves the existing DELETE endpoint, handles repeated deletion idempotently, performs best-effort object/multipart cleanup after commit, and disconnects all Socket.IO namespaces for the user.
- `darshan-server/src/auth/jwt.ts::verifyAccessToken` requires both a live session and an active, non-deleted user for every authenticated REST/socket verification. Chat, notification, and screen namespaces join a shared user room so deletion can disconnect them.
- `darshan-server/src/db/repositories/user.ts::update` locks the active non-deleted user, commits the user/password change and removes every target session in one transaction. User-facing update, reset and activation paths disconnect the same shared rooms, so a department transfer cannot continue under its old token claims.
- Normal user/operator/invite lookup paths exclude tombstones, while audit, Schedule Request and legacy Request message history can resolve a deleted creator/requester with retained name, deleted status and no exposed email. The Request projection previously returned the scrubbed tombstone address; it now returns `email: null`, and a DB-backed regression assertion is authored.
- An exhaustive production-caller search found one notification-insertion entry point. It locks and rechecks the recipient as active/non-deleted before inserting both notification and unread counter in the same transaction. Tombstoning takes the conflicting user-row update lock, so notification-first must commit before deletion or deletion-first must return `null` without either row; there is no direct production insert bypass.

### Stable resource ownership and presentation closure

- `darshan-server/src/rbac/content-ownership.ts` is the central create/read/manage/list policy and response-metadata mapper for all four resource types.
- Media, Layout, Presentation, and Schedule repositories persist stable ownership at creation and filter lists using the same ownership scope.
- Their routes return `ownership` and server-computed `permissions.can_update`/`can_delete`; CMS action controls consume those flags rather than guessing from `created_by` alone.
- Resumable upload-session create/resume/get/complete responses now embed the current Media row with the same centralized ownership/permission contract, including while PENDING; the legacy presign-create response also returns the created Media metadata. Resume, part-presign, completion, abort and idempotent retry now require both the original session creator and current authority over the Media's stable owner. A creator moved from department A to B therefore cannot continue an A-owned upload with a fresh B token. DB-backed route and deterministic transfer/finalization race assertions are authored and compile but await PostgreSQL execution.
- Direct and nested response contracts reuse `contentResponseMetadata`. Presentation detail/item/slot, Schedule item and Schedule Request expansions return `created_by`, the full ownership view and server-computed permissions for each nested owned resource.
- Presentation list/detail/update/delete and item/slot routes now apply ability plus ownership checks. Referenced layouts/media must be actor-readable and cannot be narrower than their parent resource (`ORGANIZATION` cannot contain department/restricted content; department parents cannot contain another department's content).
- Schedule item assignment similarly validates Presentation access and compatible scope. Expanded Schedule Request data is filtered through the stable Schedule, Presentation, Layout, and Media policies.
- Schedule item assignment and publication now share a transitive ownership-closure validator. It checks Schedule -> Presentation and Presentation -> Layout/Media, preventing a legacy or directly corrupted organization Presentation from smuggling department/restricted descendants into an organization Schedule snapshot. Three focused pure-unit cases pass; the DB route atomic-rejection case is authored but unexecuted.
- The DB route matrix now also includes read-only and editor custom roles, no-department create denial, ownership-filtered pagination totals, and Schedule Request control after requester transfer/tombstoning. The deleted-upload cleanup worker is exposed through one production function with a DB-backed failure/recovery/terminal/idempotency regression. These additions compile and lint cleanly but remain unexecuted while the isolated database is stopped.
- A route-by-route ability/ownership audit found that Schedule publish-history/status reads previously relied on ownership without an explicit Schedule read ability, and Schedule Request cancellation relied on ownership without ScheduleRequest update ability. Those routes now require both layers; administrator approve/reject/publish/take-down transitions also explicitly require ScheduleRequest update ability. Direct regression cases are authored but DB-unexecuted.
- Schedule-request create/list/manage/cancel uses the Schedule's stored ownership, not the current requester department, so deletion or transfer does not move operational control.

### Deletion and upload/finalization races

- Upload-session creation, idempotent resume, activation, expiry, part authorization, finalization claim, abort and final commit all use the shared current-user/session/role guard plus locked upload-session and Media rows. Legacy pending-media creation, finalization and Media deletion use the same guard.
- Resumable finalization promotes the object, then `completeFinalizationForAuthorizedActor` runs inside the guarded transaction and atomically commits completed Media only if the authenticated session is still live and the current actor still manages that stable owner. Legacy finalization also repeats the guarded Media mutation after storage inspection. If deletion, password/session revocation, disablement, demotion or department transfer committed first, neither path can make the Media playable. Authorization exceptions as well as ordinary conditional conflicts now compensate staging/canonical/source objects and provisional storage rows before returning; this closes both delayed-copy and delayed-legacy-inspection windows. If finalization obtains the user lock first, the account change waits and the completed asset is retained under its original stable owner.
- Media deletion first commits the authorized database change and makes each source/ready/thumbnail object an explicitly tracked orphan. Object-store cleanup then runs outside the transaction; successful rows are removed, while failed rows remain for the idempotent orphan-cleanup worker. That worker is now called by the existing hourly cleanup cycle. It considers only unreferenced `storage_objects` rows at least two hours old, avoiding deletion of a provisional row belonging to a currently running finalization.
- If finalization committed first, the completed Media remains under its stable owner. Deleted-user multipart/object cleanup and unreferenced compensation objects are idempotently retried by the hourly cleanup path, with a two-hour orphan grace period longer than the one-hour single-upload URL lifetime.
- Department deletion reports per-resource ownership usage and returns conflict while any Media, Layout, Presentation, or Schedule remains owned by that department.
- DB-backed route tests now use deferred object-store barriers to force the major orders without test-only production endpoints: deletion while multipart creation is still `INITIALIZING`; deletion after object promotion but before the `FINALIZING -> COMPLETED` transaction; deletion after that transaction commits but before staging cleanup returns; validation failure after deletion already changed `FINALIZING` to `ABORTED`; and validation failure after department transfer. They assert authorization rejection, multipart abort, a post-copy compensation delete with no READY Media/storage row, finalize-first retention of completed Media with unchanged stable ownership, preservation of the deletion cleanup state, and no late failure write after transfer. The tests compile/lint but have not run while PostgreSQL is stopped.
- Upload-session failure now re-enters the current-user/session/role/stable-owner guard, then locks and conditionally transitions only an expected current state in one transaction with the Media failure update. A late size/checksum/promotion result therefore cannot write after transfer or overwrite a deletion-won `ABORTED` state and retry marker. Deferred validation tests cover both deletion-first and transfer-first outcomes.
- A separate DB-backed notification race test uses PostgreSQL advisory and row locks to prove both legal orders: a notification that already holds the active-recipient share lock commits before deletion can acquire its update lock, while deletion-first causes later notification creation to return null without a row or unread counter. It compiles/lints but remains unexecuted with PostgreSQL stopped.
- The socket helper has a passing focused test that disconnects `auth:user:<id>` with `close=true` in all three authenticated namespaces: `/chat`, `/notifications`, and `/screens`. Live client disconnect and rejected reconnect remain runtime gates.

### CMS behavior

- `darshan-cms/src/api/types.ts` defines shared ownership/permission response fields and deleted-user status without requiring an email.
- `darshan-cms/src/lib/access.ts` prefers server permission flags and formats organization, department, restricted, unknown, and deleted-creator labels.
- Media, Layout, Schedule Creator, Schedule Queue, and Request Detail surfaces display stable owner/deleted-creator context; disabled actions remain visible where applicable.
- User-deletion dialogs state that access ends, incomplete uploads stop, content/schedule work remains with its existing owner, and historical creator identity remains. There is no person-to-person reassignment or restore UI.
- Focused mocked Playwright cases are authored for Media/Layouts labels and server-permission fail-closed behavior; the schedule creator test also asserts deleted-creator display without email disclosure. Discovery succeeds, but the browser cases have not been executed against the current worktree.

## Multi-Pass Corner-Case Review

1. **Identity pass:** deleted and inactive remain distinct; tombstone DELETE is idempotent; original email can be reused; deleted login/reset/update/invite activation is denied; transfer/role/password updates revoke sessions and disconnect user-facing sockets; audit attribution remains resolvable.
2. **Authorization pass:** creator, peer operator, department lead, moved creator, other department, custom role, ADMIN, and SUPER_ADMIN paths were traced over Media/Layout/Presentation/Schedule and nested references. Ability and ownership are conjunctive; creator identity alone does not bypass department ownership.
3. **Lifecycle pass:** draft, pending, approved, reserved, published, cancelled, and already-snapshotted schedule work retains stable ownership and attribution. No owner is derived from a deleted requester.
4. **Concurrency pass:** session verification versus deletion/transfer, socket reconnect, notification creation, upload create/activate/finalize, late upload validation failure, cleanup failure/retry, and account-change/finalize commit order were reviewed. A shared transaction-scoped guard now rechecks and locks the live user, session and role together with Layout, Presentation, Schedule, Schedule Request and Media writes, including upload-session state changes and both finalization paths. Source-level ordering is therefore present across all five resource families. Media deletion commits the authorized database state before external object cleanup and retains failed objects as retryable orphan records; conditional failure updates preserve a deletion-won terminal state. Deterministic two-connection tests and runtime evidence remain mandatory; source review alone is not a pass.
5. **Privacy/UI pass:** normal directories exclude tombstones; audit, Schedule Request and Request-message history show retained identity plus deleted status without the old or tombstone email; Schedule Request search cannot match the synthetic tombstone address but can still find retained name history; server flags drive mutation controls; organization/department/restricted labels are explicit. Expanded Schedule Requests reject an unreadable nested resource rather than returning a misleading partial tree.
6. **Rollout pass:** migration `0045` is additive but required before the new server. Rolling back to an older hard-delete server must disable user deletion. Migration/backfill, API/socket/object-store behavior, and old/new-version interoperability remain runtime gates.

The DB-backed migration rehearsal now has source coverage for administrator, valid department, no-department, transferred-before-migration, missing-creator and nullable-creator fixtures across all four resource tables; catalog constraints/indexes; invalid owner writes; department/creator restrictions; retained tombstone references; repeat invocation; and transactional failure followed by forward recovery. It is authored but intentionally unexecuted while isolated PostgreSQL is stopped.
