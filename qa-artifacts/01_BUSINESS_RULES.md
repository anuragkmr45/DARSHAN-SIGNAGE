## Classification

- `CONFIRMED_BUSINESS_RULE`: explicit normative contract/governance rule or a user-confirmed requirement, with its named authority. Confirmation is not proof of runtime compliance.
- `IMPLEMENTED_RULE`: source-observed behavior only. It can still be a bug or differ from the intended requirement.
- `INFERRED_RULE`: an interpretation supported by several signals, not an established requirement.
- `NEEDS_BUSINESS_CONFIRMATION`: an acceptance decision the implementation cannot settle.

Rule IDs are stable across clarification; superseded wording is corrected in place and the latest authorization decisions are BR-091..096. Historical feature inventories and old test results are not authoritative business requirements. Site-specific capacity, retention, recovery and platform targets remain separate unresolved inputs.

Evidence references use repository-relative paths and symbols where helpful. `S` in the actor/component column means server, `C` CMS, `P` player, `O` operations. These abbreviations do not replace source paths.

## Evidence Use During Test Design

For a code-backed rule with an unresolved policy, create separate implementation-characterization and intended-acceptance expectations. An observed current behavior may pass the former and fail the latter. Use `TBD - NEEDS_BUSINESS_CONFIRMATION (BQ-xxx)` where an answer is required; do not default to whatever the code does.

No rollback, backup completeness, transport security, accessibility, capacity or feature-completeness claim is proven by this catalogue. Detailed cases are ready for QA, with actual results and execution evidence left blank for authorized isolated-environment testing.
