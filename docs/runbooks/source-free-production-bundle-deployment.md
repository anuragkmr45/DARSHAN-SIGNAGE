# Source-Free Production Bundle Deployment

Last code-truth refresh: 2026-09-24.

This is the canonical procedure for the production profile generated by:

- `scripts/bundle/build-production-bundle.mjs`
- `scripts/bundle/assemble-runtime-bundle.sh`
- `scripts/bundle/install-signed-role.sh`
- the generated role scripts inside each signed archive

Do not replace these commands with old `docker compose` notes, `npm run seed`,
`db:push`, or manual edits on a production VM.

## 1. What "source-free" Means

The production artifact contains no Git checkout, TypeScript application
source, source maps, TypeScript compiler, or `tsx` runtime. It contains:

- OCI/Docker image archives for released services
- compiled backend JavaScript and compiled production CLI commands
- the built CMS web assets
- Electron installers and generated player configuration
- generated Compose, TLS, policy, health, and lifecycle files
- signed role and transfer manifests

Compiled JavaScript can still be inspected and copied. "Source-free" means no
source checkout or build toolchain is deployed; it is not source-code secrecy or
DRM.

## 2. Production Topology And TLS

The generated server transfer set has six roles:

| Role | Normal target |
|---|---|
| `data` | Data VM: PostgreSQL, MinIO, private exporters, TLS metrics gateway |
| `valkey` | Valkey VM: Valkey, private node exporter, TLS metrics gateway |
| `backend` | Backend VM: API, worker, private node exporter, TLS metrics gateway |
| `cms` | CMS VM: Nginx CMS/proxy, private exporters, TLS metrics gateway |
| `observability` | Observability VM: Prometheus, Alertmanager, Grafana, node exporter |
| `recovery` | Isolated recovery VM: one-shot restore rehearsal only |

The Electron player is installed separately on player machines.

All cross-VM application and monitoring traffic uses TLS with certificate
verification:

- browser and player to CMS: HTTPS
- CMS to Backend, Data, and Grafana: HTTPS
- player to Backend: HTTPS/WSS
- player media URLs: HTTPS through the CMS object proxy
- Backend to PostgreSQL: TLS with server identity verification
- Backend to Valkey: authenticated `rediss://`
- Backend to MinIO and off-host S3: HTTPS
- Prometheus to remote role metrics gateways, Backend, and MinIO: HTTPS
- direct Prometheus, Alertmanager, and Grafana listeners: HTTPS

Raw node, PostgreSQL, and Nginx exporters are private Compose services and are
not published on the VM. The default remote metrics gateway port is `9443`.

## 3. Establish Trust Before Building

### 3.1 Release signing key

Create this once on the controlled build/release-authority machine. Do not use
`sudo openssl ... -out /secure/...` before giving the build user ownership of
the protected directory.

```bash
sudo install -d -m 700 -o "$USER" -g "$USER" /secure/darshan-signing
openssl genpkey \
  -algorithm RSA \
  -pkeyopt rsa_keygen_bits:3072 \
  -out /secure/darshan-signing/release-signing.key
chmod 600 /secure/darshan-signing/release-signing.key
openssl pkey \
  -in /secure/darshan-signing/release-signing.key \
  -pubout \
  -out /secure/darshan-signing/release-signing.pem
chmod 644 /secure/darshan-signing/release-signing.pem
openssl pkey -pubin \
  -in /secure/darshan-signing/release-signing.pem \
  -outform DER | sha256sum
```

Record and approve that public-key fingerprint through an independent channel.
Before transferring any release, pin the approved public key on every server
VM, including Recovery:

```bash
sudo install -d -m 755 -o root -g root /etc/darshan/trust
sudo install -m 644 -o root -g root \
  /secure-channel/release-signing.pem \
  /etc/darshan/trust/release-signing.pem
openssl pkey -pubin \
  -in /etc/darshan/trust/release-signing.pem \
  -outform DER | sha256sum
```

The public key is not trusted merely because it arrived beside a release.

### 3.2 Recovery attestation key

Create a separate RSA keypair for the recovery authority. Do not reuse the
release signing key.

```bash
sudo install -d -m 700 -o root -g root /secure/darshan-recovery
sudo openssl genpkey \
  -algorithm RSA \
  -pkeyopt rsa_keygen_bits:3072 \
  -out /secure/darshan-recovery/attestation.key
sudo chmod 600 /secure/darshan-recovery/attestation.key
sudo openssl pkey \
  -in /secure/darshan-recovery/attestation.key \
  -pubout \
  -out /secure/darshan-recovery/attestation.pem
sudo chmod 644 /secure/darshan-recovery/attestation.pem
```

Keep `attestation.key` only under recovery-authority control. Pin only its public
key on the Backend VM:

```bash
sudo install -m 644 -o root -g root \
  /secure-channel/attestation.pem \
  /etc/darshan/trust/recovery-attestation.pem
```

### 3.3 Site transport and device PKI

Create the site PKI once and preserve it across releases:

```bash
sudo install -d -m 700 -o "$USER" -g "$USER" /secure/darshan-pki
bash scripts/bootstrap/create-site-pki.sh \
  --site-name site-a \
  --output-dir /secure/darshan-pki/site-a
```

Back it up offline. Never deploy `transport-ca.key`. Preserve `device-ca.key`
because the Backend uses it to issue player certificates.

## 4. Prepare And Build The Artifact

The build machine requires Git, Docker Engine, Docker Compose v2, OpenSSL,
Node 20, npm, tar, jq, and enough disk for the image build plus six archives.

```bash
git clone <approved-repository-url> DARSHAN-SIGNAGE
cd DARSHAN-SIGNAGE
git switch release-01
git status --short
node --version
docker version
docker compose version
openssl version
```

Create one private configuration file:

```bash
export SITE_NAME=site-a
export RELEASE_ID=2026-09-24-r1
install -d -m 700 deploy/production/bundles
cp deploy/production/bundle.env.example \
  "deploy/production/bundles/${SITE_NAME}-${RELEASE_ID}.env"
chmod 600 "deploy/production/bundles/${SITE_NAME}-${RELEASE_ID}.env"
```

Edit only that private file. Important values include:

- `RELEASE_ID`, `SITE_NAME`, all service hosts and exact bind addresses
- `TRANSPORT_TLS_MODE=internal-ca` or `provided`
- `RELEASE_SIGNING_PRIVATE_KEY=/secure/darshan-signing/release-signing.key`
- stable external volume names and provisioning mode
- all runtime credentials
- measured capacity evidence and per-service resource limits, or an explicit
  owner-approved capacity waiver expiring within 90 days
- minimum free disk policy for every VM role
- one explicit backup mode: independently operated off-host storage, or the
  accepted-risk Data-VM `EXTERNAL_SIDECAR` policy with its site-scoped host path
- `INSTALL_PLAYWRIGHT_CHROMIUM=true`
- player target platforms and native installer inputs

For a fresh site use `VOLUME_PROVISIONING_MODE=create`. For an update use
`require-existing` and explicitly copy the six deployed volume names into the
new configuration. Do not assume volume names.

`CAPACITY_VALIDATION_MODE=waived` is a temporary release-risk acceptance, not
capacity evidence. It requires an approval authority, reason and future expiry;
the signed operations policy records all three. Replace it with `measured` and
an approved evidence file before the waiver expires.

Validate, build, and verify:

```bash
bash scripts/bundle/build-production-bundle.sh --validate-only \
  "deploy/production/bundles/${SITE_NAME}-${RELEASE_ID}.env"

bash scripts/bundle/build-production-bundle.sh \
  "deploy/production/bundles/${SITE_NAME}-${RELEASE_ID}.env"

cd "dist/onprem/${SITE_NAME}/${RELEASE_ID}"
DARSHAN_RELEASE_TRUST_KEY=/secure/darshan-signing/release-signing.pem \
  ./verify-bundle.sh
```

The builder stages output and atomically publishes exactly:

```text
dist/onprem/<site>/<release-id>/
```

It refuses to overwrite an existing release. Do not deploy a build containing
`*.SKIPPED.txt`; that is structural test output without real image archives.

The generated `transfer/` directory contains six role archives, the signed
transfer manifest, its signature, and the installer. The installer itself is
covered by the signed transfer manifest.

## 5. Prepare Target VMs And Firewall

Each server VM requires:

- Docker Engine and Docker Compose v2
- a `docker` group and an approved deployment user in that group
- OpenSSL, curl, tar, jq, sha256sum, df, stat, flock, readlink, and getent
- the independently pinned release public key
- enough free space on the transfer, `/var/tmp`, release, Docker data-root, and
  Backend worker-scratch filesystems

Do not install Node.js on production VMs for this workflow. Production CLI
commands run from compiled JavaScript inside the backend image.

Apply a source/port firewall allowlist before starting services:

- operator and player networks to CMS HTTPS
- player and CMS VM networks to Backend HTTPS/WSS
- Backend VM to Data PostgreSQL TLS and MinIO HTTPS
- Backend VM to Valkey TLS and, for `APPLICATION_OFFHOST`, approved off-host S3 HTTPS
- CMS VM to Data MinIO HTTPS and Observability Grafana HTTPS
- Observability VM to each role's TLS metrics gateway, Backend metrics HTTPS,
  and MinIO metrics HTTPS
- approved operator network to direct Prometheus, Alertmanager, and Grafana
  HTTPS only when those consoles are intentionally exposed
- Recovery VM only to the configured backup source and isolated recovery targets

Deny PostgreSQL, Valkey, MinIO Console, metrics gateways, and observability
listeners from all other sources. Use the configured ports in the signed role
environment; do not assume the example defaults.

## 6. Verify And Install A Role Archive

Transfer only these files to each VM through the approved channel:

- that VM's `<site>-<release>-<role>.tgz`
- `TRANSFER_MANIFEST.sha256`
- `TRANSFER_MANIFEST.sig`
- `install-signed-role.sh`

Do not transfer the Git checkout, private bundle env, release private key,
transport CA private key, or recovery attestation private key.

On each VM, verify the signature before executing the transferred installer:

```bash
export SITE_NAME=site-a
export RELEASE_ID=2026-09-24-r1
export ROLE=data
export ARCHIVE="${SITE_NAME}-${RELEASE_ID}-${ROLE}.tgz"
transfer_dir="/tmp/darshan-${RELEASE_ID}-${ROLE}"
install -d -m 700 "$transfer_dir"
umask 077

# Transfer the four approved files into this directory, then lock their modes.
chmod 600 "${transfer_dir}/${ARCHIVE}" \
  "${transfer_dir}/TRANSFER_MANIFEST.sha256" \
  "${transfer_dir}/TRANSFER_MANIFEST.sig"
chmod 700 "${transfer_dir}/install-signed-role.sh"
cd "$transfer_dir"

openssl dgst -sha256 \
  -verify /etc/darshan/trust/release-signing.pem \
  -signature TRANSFER_MANIFEST.sig \
  TRANSFER_MANIFEST.sha256

grep -E "  (${ARCHIVE}|install-signed-role[.]sh)$" \
  TRANSFER_MANIFEST.sha256 > selected-transfer.sha256
test "$(wc -l < selected-transfer.sha256)" -eq 2
sha256sum -c selected-transfer.sha256

sudo ./install-signed-role.sh \
  --archive "$ARCHIVE" \
  --role "$ROLE" \
  --release-root "/opt/darshan/${RELEASE_ID}"

rm -f selected-transfer.sha256 "$ARCHIVE" \
  TRANSFER_MANIFEST.sha256 TRANSFER_MANIFEST.sig install-signed-role.sh
cd /tmp
rmdir "$transfer_dir"
```

Repeat with `ROLE=valkey`, `backend`, `cms`, `observability`, or `recovery` on
the corresponding VM, and `ROLE=media` when the optional LIVE role is included.
The installer:

1. copies the signed inputs into protected `/var/tmp` storage after a capacity
   preflight;
2. verifies the transfer signature against the pinned key;
3. verifies the selected archive checksum;
4. rejects traversal, links, devices, sockets, and oversized entry sets;
5. checks expanded release-disk capacity;
6. extracts to a partial directory;
7. verifies the signed role and Compose model; and
8. atomically moves the role into `/opt/darshan/<release>/<role>`.

It never overwrites an existing role directory.

## 7. Fresh Five-VM Installation

Scheduled LIVE adds an optional sixth Media VM through `INCLUDE_LIVE_MEDIA=true`.
It receives a signed `media.tgz` with the pinned offline media image; all live
private inputs are generated/provisioned on target. Follow
[Sixth Media VM deployment](live-media-vm-deployment.md) after the existing roles.
Runtime remains OFF until explicit activation and integrated release QA.

The required order is:

1. Data
2. Valkey
3. Backend initial phase
4. CMS
5. Backend final acceptance
6. Observability
7. Players

### 7.1 Data VM

```bash
cd "/opt/darshan/${RELEASE_ID}/data"
sudo ./prepare-host.sh
./load-images.sh
./start.sh
./health-check.sh
```

`prepare-host.sh` creates or validates the stable external volumes. The start
path creates the least-privilege PostgreSQL monitoring role and then starts its
exporter. The health check proves PostgreSQL TLS, MinIO HTTPS, both exporters
through the TLS gateway, and the signed disk threshold.

### 7.2 Valkey VM

```bash
cd "/opt/darshan/${RELEASE_ID}/valkey"
sudo ./prepare-host.sh
./load-images.sh
./start.sh
./health-check.sh
```

The health check performs an authenticated TLS Valkey command and verifies the
node exporter through the TLS gateway. Plaintext Valkey is disabled.

### 7.3 Backend VM, initial phase

```bash
cd "/opt/darshan/${RELEASE_ID}/backend"
sudo ./prepare-host.sh
./load-images.sh

umask 077
read -r -s -p 'Initial administrator password: ' password; printf '\n'
printf '%s\n' "$password" > bootstrap-secrets/admin-password
unset password
chmod 600 bootstrap-secrets/admin-password

./deploy.sh
```

For an empty database, `deploy.sh` resumes or begins `INSTALL`, applies the
signed migration set, runs protected administrator bootstrap once, starts API
and worker, and performs Backend login acceptance. It then stops at
`BACKEND_ACCEPTED`; this is expected because CMS is not running yet.

Do not run `npm run seed`, `db:push`, `migration:adopt`, or a password reset.

### 7.4 CMS VM

```bash
cd "/opt/darshan/${RELEASE_ID}/cms"
sudo ./prepare-host.sh
./load-images.sh
./start.sh
./health-check.sh
```

This verifies the CMS HTTPS page, Backend proxy, a real WebSocket `101`
upgrade, and the private exporters through the CMS TLS metrics gateway.

### 7.5 Finish Backend acceptance

```bash
cd "/opt/darshan/${RELEASE_ID}/backend"
./finalize-install.sh
./health-check.sh
```

This tests Backend and CMS login, marks the installation complete, and removes
`bootstrap-secrets/admin-password`. If interrupted earlier, rerun `deploy.sh`;
the deployment ledger resumes from the recorded step. If interrupted after
`BACKEND_ACCEPTED`, rerun `finalize-install.sh`.

### 7.6 Observability VM

```bash
cd "/opt/darshan/${RELEASE_ID}/observability"
sudo ./prepare-host.sh
./load-images.sh
./start.sh
./health-check.sh
```

The health check requires Prometheus, Alertmanager, and Grafana HTTPS plus every
generated scrape target reporting `up == 1`.

## 8. Independent Restore Rehearsal

A successful backup upload is not restore proof. Before an upgrade or legacy
database adoption, restore a selected off-host backup into clean, isolated
PostgreSQL and S3/MinIO targets.

Install and prepare the signed Recovery role on an isolated Recovery VM:

```bash
cd "/opt/darshan/${RELEASE_ID}/recovery"
sudo ./prepare-host.sh
sudo ./load-images.sh
```

Install these six files as root-owned mode `0600` under `./inputs`:

```text
source-access-key
source-secret-key
target-database-url
target-s3-access-key
target-s3-secret-key
attestation-private-key
```

Example installation:

```bash
sudo install -m 600 -o root -g root \
  /secure/recovery/source-access-key ./inputs/source-access-key
sudo install -m 600 -o root -g root \
  /secure/recovery/source-secret-key ./inputs/source-secret-key
sudo install -m 600 -o root -g root \
  /secure/recovery/target-database-url ./inputs/target-database-url
sudo install -m 600 -o root -g root \
  /secure/recovery/target-s3-access-key ./inputs/target-s3-access-key
sudo install -m 600 -o root -g root \
  /secure/recovery/target-s3-secret-key ./inputs/target-s3-secret-key
sudo install -m 600 -o root -g root \
  /secure/darshan-recovery/attestation.key ./inputs/attestation-private-key
```

The target database URL should require TLS and can reference the supplied CA at
`/run/darshan-recovery/transport-ca.crt`. The target database and every expected
object bucket must be empty.

Run the rehearsal with the real backup run ID, manifest object key, approved
isolated target ID, and recovery object-store endpoint:

```bash
sudo ./restore-rehearsal.sh \
  --manifest-key 'darshan/site-a/runs/<run-id>/manifest.json' \
  --confirm-run-id '<run-id>' \
  --target-id 'isolated-recovery-01' \
  --target-s3-endpoint 'https://recovery-minio.example.net' \
  --target-s3-region 'us-east-1'
```

The command refuses a target matching the signed production database or object
store, including DNS aliases resolving to the same endpoint. It verifies the
manifest, artifact lengths and hashes, tar paths and types, extraction capacity,
restored object lengths and hashes, and application consistency. Only then does
it write `./evidence/<run-id>.json` with an RSA-SHA256 attestation.

Copy the evidence to a protected Backend path:

```bash
sudo install -d -m 750 -o root -g docker /secure/darshan-recovery/evidence
sudo install -m 640 -o root -g docker \
  "./evidence/<run-id>.json" \
  "/secure/darshan-recovery/evidence/<run-id>.json"
```

Evidence is accepted only when the signature matches the independently pinned
recovery public key, the site and off-host policy match, and the timestamp is no
older than `max(24 hours, BACKUP_INTERVAL_HOURS)`.

## 9. Controlled Update

Build the new release with the same site PKI and explicit existing volume names.
Use `VOLUME_PROVISIONING_MODE=require-existing`. Install each updated role under
a new `/opt/darshan/<new-release>/` directory; never overwrite an old release.

For a full release, install and prepare Data and Valkey first, then Backend,
CMS, and Observability. Compatibility checks compare the signed, source-controlled
compatibility generation before a dependent role starts. A breaking generation
requires coordinated role and player rollout; a same-generation role can be
updated selectively only after its release notes and migration plan confirm
semantic compatibility.

Before Backend deployment, create fresh restore evidence as described above.
Then on the new Backend role:

```bash
cd /opt/darshan/<new-release>/backend
sudo ./prepare-host.sh
export DARSHAN_BACKUP_MANIFEST=/secure/darshan-recovery/evidence/<run-id>.json
export DARSHAN_RECOVERY_ATTESTATION_PUBLIC_KEY=/etc/darshan/trust/recovery-attestation.pem
./deploy.sh
unset DARSHAN_BACKUP_MANIFEST DARSHAN_RECOVERY_ATTESTATION_PUBLIC_KEY
./health-check.sh
```

The upgrade sequence is deliberately a maintenance window:

1. verify role signature, compatibility, images, restore evidence, and
   dependency reachability;
2. record or resume the `UPGRADE` deployment run;
3. stop API and worker;
4. apply forward migrations with the compiled CLI;
5. recreate API, worker, and Backend metrics services from the new role;
6. require strict readiness and health; and
7. atomically mark the new Backend release active.

There is no automatic database downgrade. If migration fails, leave API and
worker stopped, retain logs and the deployment record, and execute the approved
database/object restore plan. Do not simply start an old image against a schema
whose compatibility has not been proven.

For a backend-only update, transfer only the new Backend archive. Do not replace
the Data or Valkey archives merely because the Backend changed. The update is
allowed only when the deployed dependencies report the same signed compatibility
generation, the existing TLS names/CA and credentials remain valid, and the
migration plan is approved.

Old and new release folders share stable per-site Compose projects and external
volumes. `stop.sh` refuses to act from a stale release folder, preventing an old
directory from stopping the active release. Never use `docker compose down -v`.

## 10. Existing Untracked Database Adoption

If `deploy.sh` reports an existing untracked database, do not invent a token and
do not seed or reset it. Obtain the real approved change-ticket identifier from
your change-management system, create valid signed restore evidence, and run:

```bash
cd "/opt/darshan/${RELEASE_ID}/backend"
export DARSHAN_BACKUP_MANIFEST=/secure/darshan-recovery/evidence/<run-id>.json
export DARSHAN_RECOVERY_ATTESTATION_PUBLIC_KEY=/etc/darshan/trust/recovery-attestation.pem
./adopt-existing.sh --ticket CHG-1234
unset DARSHAN_BACKUP_MANIFEST DARSHAN_RECOVERY_ATTESTATION_PUBLIC_KEY
```

`CHG-1234` is an example audit reference, not a secret token. The script records
the exact string, validates the database fingerprint and migration plan, adopts
the ledger, applies forward migrations, and records the existing active
`SUPER_ADMIN` without changing its password. An interrupted adoption must be
resumed with the same ticket.

## 11. Players

Ubuntu example:

```bash
sudo apt install -y ./electron/installers/*.deb
sudo install -d -m 755 /etc/darshan/player
sudo install -m 644 electron/config.json /etc/darshan/player/config.json
sudo install -m 644 electron/transport-ca.crt /etc/darshan/transport-ca.crt
```

Windows installs `config.windows.json` as
`C:\ProgramData\DARSHAN\config.json` and the CA as
`C:\ProgramData\DARSHAN\transport-ca.crt`.

Verify fullscreen kiosk behavior, pairing, HTTPS API, WSS realtime, media/PDF
download and cache, schedule/default media, heartbeat, reboot recovery, and
offline playback. The player rejects a Backend with a different compatibility
generation.

## 12. Acceptance Evidence

A release is not proven by successful archive creation alone. Retain redacted
evidence for:

- build provenance, bundle signature, transfer signature, and role signatures
- image-load preflight and actual image IDs/platforms
- fresh five-VM install and interrupted-install resume
- Backend and CMS login
- real WebSocket `101` upgrade
- upload, PDF conversion/preview, Chromium webpage capture, FFmpeg processing,
  player download/cache/playback, and offline playback
- PostgreSQL, Valkey, MinIO, CMS, Backend, and observability TLS verification
- all Prometheus targets and Grafana access
- nonempty restore rehearsal covering media and all configured log buckets
- backend-only update against populated data
- failed migration and approved restore response
- wrong CA, tampered manifest/archive, low disk, missing credential, and
  incompatible-generation rejection

Repository validation commands are necessary but do not replace this staging
exercise:

```bash
bash scripts/verify/validate-source-free-production-bundle.sh
sudo DARSHAN_VERIFY_IMAGE_LOADER=true \
  bash scripts/verify/validate-source-free-production-bundle.sh
```

The second form is intended for an isolated root-capable CI host because it
creates unique test volumes and host-preparation state, then removes only those
uniquely named resources.

## 13. Rollback And Decommissioning

Application rollback and data recovery are separate decisions:

- Before any migration, an active role can be stopped and a prepared previous
  role restarted after compatibility review.
- After a migration, do not assume the previous image supports the new schema.
  Use the approved recovery plan and signed restore evidence.
- Preserve stable PostgreSQL, MinIO, Valkey, Prometheus, Alertmanager, and
  Grafana volumes unless an independently approved decommission procedure says
  otherwise.
- Never delete a production database or volume as a normal software update.
- Never regenerate the site transport or device CA as a rollback shortcut.
- Never run `down -v`, delete an old release, or prune Docker storage until the
  new release and recovery evidence have passed acceptance and retention policy.
