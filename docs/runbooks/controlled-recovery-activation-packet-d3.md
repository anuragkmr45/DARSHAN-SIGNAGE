## Safety and resume contract

D1 is strict before stage one: any running/retained container blocks admission. After stage one, readiness admits only the exact retained D3 IDs, labels and caps recorded by the last receipt. Partial, changed, unexpected or foreign resources fail closed. Every stage rechecks available RAM, swap and pressure. The maximum serial stage is API + player + controller + PostgreSQL + MinIO + Valkey: 2,080 MiB; the 512 MiB host reserve makes the exact gate 2,592 MiB (2,717,908,992 bytes).

The physical source target identity is stable for the operation, while mutable content may change during seed/backup. `STOP_SOURCE_APPLICATION` seals the content identity; every later stage must observe that exact seal. Resume compares live physical/content/resource/invariant truth but returns the retained duration, peak-memory and swap receipt—measurements are never fabricated from equality.

The fixed boundaries cover exact Docker resource shapes, cgrouped host roles, schema `0057` seed classes, deterministic PNG/PDF/offline-HTML plus checked-in MP4, a protected disposable age identity and broker path, controlled A/B/C interruption/resume, CMS Chromium, actual Electron on `DISPLAY=:0`, worker drain, separate promotion, rollback under freeze, evidence retention and exact owned cleanup. Firefox is never launched or signalled. Failure retains resources.

Restart uses the durable journal as a completed prefix. Readiness is evaluated for the next stage with exact retained resources, and only the newest authoritative checkpoint is compared with live state. Older seed/backup mutable hashes are not re-compared after the stop-stage content seal; their measured duration, peak and swap evidence remains immutable. The non-test composition constructs the exported Packet 1 adapter and prepare/resume workflow, Packet 2 preparation, and exported promotion/rollback workflow. Missing low-level system authority fails the stage; there is no production-path injected-success action map.

API and worker processes use the supported `DARSHAN_CONFIG_FILE` plus `DATABASE_URL_FILE`, `JWT_SECRET_FILE`, `MINIO_ACCESS_KEY_FILE`, `MINIO_SECRET_KEY_FILE` and `VALKEY_URL_FILE`. They run from the fixed `runtime-empty` directory with a fixed empty dotenv path, loopback API/device ports, disposable TLS paths and inspected bridge addresses. PostgreSQL has two enrolled shapes: a bounded official-entrypoint init phase using `POSTGRES_PASSWORD_FILE` and a final numeric `70:70`, cap-drop/read-only-root runtime with a data volume, `/run/postgresql` tmpfs and fixed health check.

The generated backend environment must pass the real production config loader before either process is eligible to launch. This includes signature-only device authentication, every backup repository/retention/capacity/V2 broker/keyring/encryption/capsule identity, TLS selectors and exact `release-03`/site authority. No prebuilt restore request is accepted: the backup stage durably publishes the exact operation/site/release/run/manifest receipt, and restart derives the request from that receipt or fails closed on any mismatch.

CMS validation uses the checked-in login selectors and supported settings/backups/status/history/download and content APIs; there is no D3-only application endpoint. The checked-in controller has no caller path/endpoint/argv surface: it loads the fixed D3 activation, verifies every asset and host-tool identity, observes and verifies the exact Docker tool image/config/labels, then asks the fixed boundary factory to construct the typed composition/journal boundary.
