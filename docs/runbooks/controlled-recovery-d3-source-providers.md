# D3 fixed source provider preparation

The new [static recovery-prefix observer](controlled-recovery-d3-recovery-prefix.md) adds one fixed read-only command under the already enrolled live-seed gate. It verifies the retained migration-only prefix without changing source/data profiles or existing data-status refusal. It remains review-gated; no live invocation is authorized by its implementation.

This development-only entrypoint composes the verified foundation layout, exact Docker executor, protected state, numeric volume materializer, certificate-bound health probes and D1 admission. `providers_enabled:true` and `live_prepare_enabled:true` authorize preparation. The separate [2B1 data profile and runbook](controlled-recovery-d3-source-data.md) add fixed `seed` and read-only `data-status` commands; `live_seed_enabled:true` remains separately enrolled after review, while another seed invocation still requires explicit authorization and complete prefix admission. `capture_enabled:false`, legacy `source_backup.enabled:false`, D2 `enabled:false` and `whole_run_enabled:false` keep capsule/broker/capture and whole-run recovery closed. The installed full-backup factory and recovery `constructBoundary` remain unavailable.

Use that same command with its sole final word replaced by `status` for current authenticated health, or `stop` for retained-resource settlement. No extra arguments, endpoints, images, paths or commands are accepted. `capture` and `resume` fail before provider loading at the missing backup dependencies. There is also `npm run controlled-recovery:d3-source -- <fixed-command>`; the clean-environment Node invocation above makes the installed Node authority explicit.

The reviewed pending-create retry is an explicit exception to the initial EMPTY/READY preflight rule: preflight/status remain BLOCKED and strictly unchanged when an intent is pending. A deliberate `prepare` under both controller and source command locks may reconcile exactly one pending resource at the next position of the retained ordered source prefix. It loads the durable intent, reconstructs the fixed configuration, re-inspects every identity field and consumer, reruns admission, and re-inspects before appending immutable reconciliation/created receipts. Network/volume recovery requires exact intent/configuration/labels/identity and unique fixed-name observation. A container additionally requires the protected full-ID cidfile to equal the inspected full ID, Docker state created/unstarted with zero start/finish timestamps, zero PID/restart count, no running/dead/restarting/OOM state and no durable start evidence. Name alone is never authority.

Docker capability observations accept the exact planned uppercase capability set with or without one canonical `CAP_` prefix. Normalization preserves identity; duplicates, unknown/missing/extra capabilities, repeated prefixes and lowercase/mixed-case ambiguity fail. Docker 29's `CAP_CHOWN` and related spelling therefore no longer reject the enrolled PG-init plan.

Start intents are now durable before start dispatch. Exact unstarted retained prefixes can continue after reconciliation/cancellation without duplicate creation or start; previously started stopped/exited containers are not restarted. Runtime-prefix continuation requires the immutable materialization binding published only after successful protected materialization. Unknown, gapped, multiple-pending, changed, foreign or previously started pending state remains blocked. Cancellation after reconciliation preserves the exact created ID and prevents start. Successful prepare reports `reconciledRoles`; reconciliation/start/materialization receipts remain protected evidence rather than SQL or backup success.

Whenever any PostgreSQL/MinIO/Valkey runtime resource is retained, common observation validates materialization authority before reporting readiness, including a complete READY topology and repeat prepare. The canonical binding must match operation/site/repository/profile, current verified layout, exact retained volume/init prefix and materializer evidence digest. The materializer receipt must itself match the current fixed host-layout file inventory (all hashes, sizes, roles and destinations) and current re-observed volume identities. Recomputing a changed receipt/binding pair's digests does not bypass this comparison. Missing, changed, noncanonical, unsafe-mode or hardlink commit-window receipts block; no receipt is recreated or recovered through common observation, even during repeat prepare. The init-only prefix before materialization remains allowed without a binding. Initial materialization still performs its existing actual volume owner/mode/hash inspections; retained-proof validation creates no helper and claims no new live file measurement.

`preflight` and `status` do not create source directories, secrets, receipts or locks, and do not recover publication links or remove pending artifacts. Unsafe commit-window state is reported blocked for reviewed recovery. Preflight re-observes empty-or-exact retained topology and D1 readiness; it does not claim live TLS success. Status re-runs real positive/negative health when the retained source has reached service readiness. JSON contains public codes, next action, headroom/pressure evidence and retained IDs; a blocked report explicitly marks ownership as unverified. Journals are indexes, not current Docker authority. Exit status is 0 for successful reports, 3 for invalid input, and 5 for blocked/failure.

Populated status uses separate read-only Docker, health, layout and target observers. The target observer opens only retained canonical state and never falls back to or syncs cidfiles. Its executor admits only list/inspect operations. Health may connect to the retained running services and read existing protected credential/CA files, but it cannot invoke mutating layout verification. A hardlink commit window, pending artifact, unsafe mode or active layout lock returns blocked without repair. The regression uses actual retained CA/TLS files and journal receipts, fake Docker/network transports, and unchanged before/after inode, link, path, mode, ownership, mtime/ctime and content-digest inventories; ordinary read-access timestamps are outside that comparison.

Mutations share the protected `.controlled-recovery-d3/run/controller-source.lock` and the existing source command lock. Every create/start/stop dispatch and materializer helper rechecks admission. Exact reserved create intents are allowed only within the current owned lock, before that role exists; any observed same-name resource or extra pending intent is rejected. IDs remain durable before start. D1 runs unchanged through an adapter that excludes only fully re-observed retained owned container IDs from its foreign-workload check. Foreign running containers, including unrelated workloads, still fail. Stopped foreign volume consumers and subnet collisions fail too.

Admission checks enrolled images/context/daemon/socket/clean Docker config, the root-supplied MinIO capability evidence, D1 artifact/disk/inode readiness, the unchanged 2717908992-byte available-memory requirement, swap/pressure limits, and Firefox file identity before/after admission and operation. Missing pressure is blocked. No Firefox process is stopped or changed. The fixed service/container/helper caps remain unchanged. There are no pulls/builds/prune/Compose/public ports/restart policies/socket mounts.

Preparation retains secrets/one CA/TLS, officially initializes and joins PG, materializes only owned volumes with numeric 0700/0600 ownership, starts exact enrolled services and verifies real positive/negative TLS probes. Success records at most `LAYOUT_READY` and `SERVICES_READY`; no later stage or backup success is manufactured. Repeating `prepare` on a complete retained ready topology re-verifies it without new creates.

For cleanup, first use `preflight`/`status`, then the fixed `stop` command for a complete exact nonforeign topology. A middle-stop failure permits retry across mixed running/stopped services; all exact IDs are joined before the stop receipt. `stop` retains stopped containers, network, volumes, keys, layout and journal evidence. It never deletes source data or unattributed old anonymous volumes, and a stopped operation cannot restart automatically.

Partial/pending resources outside the exact retry contract above, and all foreign, changed, malformed or uncertain resources, require inspection of the public retained-ID index and protected receipts/cidfiles plus independent Docker inspection. Do not adopt resources by name or delete volumes by prefix. Preserve stale/uncertain controller, source, layout and helper locks; PID reuse never authorizes takeover. An unjoined process must be settled and exact ownership independently established before a separate cleanup/recovery packet. No destructive cleanup CLI is installed.
