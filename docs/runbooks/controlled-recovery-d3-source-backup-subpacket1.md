# D3 source and encrypted backup — static subpacket 1

Concrete providers and their live-acceptance blockers are documented in [subpacket 2A](controlled-recovery-d3-source-subpacket2a.md). The interface-only status below is the historical subpacket 1 boundary; source activation remains disabled.

This subpacket provides a protected source profile, durable source state and typed service lifecycle. It does not install a source command driver or create a source, migrate a database, seed data, produce a capsule, reserve a backup or capture/encrypt/publish a backup. `source_backup.enabled` and `whole_run_enabled` remain false; D2 remains disabled and the installed whole-run factory remains unavailable. No Docker command or application effect was run for this subpacket.

The runtime profile/schema fix the source root under `.controlled-recovery-d3/source`, 0700 directories/0600 files, existing `darshan-d2-20261030` names, internal `172.30.250.0/28` network, exact service IPs, PG 70:70 runtime, developer numeric MinIO/Valkey users, TLS/file credentials, SCRAM, browser-off MinIO, TLS-only authenticated Valkey, persistence/memory bounds, finite health probes and the exact five future capsule roles. Service memory/CPU/PID limits come from the enrolled D2 profile; they are not enlarged here. The age private key is excluded from capsule authority and disposable signing keys must be distinct.

The only command parser accepts exactly one of `prepare`, `capture`, `resume`, `status`, `stop`. It accepts no endpoints, commands, database names, image/mount choices or target paths. `D3SourceBackupController.execute` is the fixed command entrypoint; `loadInstalledD3SourceBackup()` deliberately fails with `CONTROLLED_RECOVERY_D3_SOURCE_BACKUP_DEPENDENCIES_NOT_ENROLLED`. There is no newly installed runnable CLI to invoke.

The fixed durable stage order is:

`LAYOUT_READY → SERVICES_READY → SCHEMA_READY → SEEDED_AND_SEALED → CAPSULE_READY → BACKUP_RESERVED → PUBLICATION_VERIFIED → SOURCE_STOPPED`.

Receipts bind operation/site/repository/profile, previous receipt, evidence and complete exact resource inventory. Each resource has a durable creation intent before create; its returned ID/identity is durably recorded before start/use. Volume identity uses its actual local Docker metadata fingerprint, including creation time and mountpoint, because Docker named volumes have no independent immutable container-style ID. Retired PG-init identity remains history. Publication uses canonical owner-only files, exclusive links, fsync, immutable identical retry semantics and exact crash-window recovery. Foreign/profile-changed/corrupt/gapped state fails. Mutating commands share an exclusive protected operation lock; a stale lock is retained for explicit investigation rather than stolen by PID or age. `status` reports an in-progress command without claiming verification.

With real providers supplied by a later reviewed factory, `prepare` can complete layout and source-service readiness. Repeated preparation re-observes exact retained IDs and re-runs authenticated health checks. `capture` and `resume` re-observe base truth but remain closed at the missing schema/data/capsule/broker/capture boundary. `status` verifies layout and current Docker/TLS health for the first two stages; any later journal stages are reported unverified. Journals never replace SQL, object or repository verification.

`stop` stops and joins only the exact currently retained service container IDs. Topology identity is separate from running-state convergence: a complete, exact topology with a mixture of running/stopped services can retry `stop`, stopping the remaining running IDs and joining every retained service ID. A middle-stop failure leaves no stop receipt; the retry records one only after every service is observed stopped. `status` reports `SOURCE_STOP_INCOMPLETE` with `nextCommand:stop` for this complete mixed state. For an interrupted operation, the separate stop receipt preserves the completed stage prefix; it does not invent the final successful `SOURCE_STOPPED` phase or claim a completed backup. A fully stopped source cannot restart automatically. Missing/pending/foreign/changed resources, unexpected consumers, subnet collision or incomplete topology remain blocked. No adoption by name, prune, Compose, image pull/build, socket mount, restart policy or public port is permitted.

Every source observation inspects mounts for all listed containers, including stopped containers with unrelated names or networks. Any named-volume or bind consumer of a source PostgreSQL/MinIO/Valkey volume outside the exact retained owned container set is refused before effects; read-only foreign mounts are consumers too. Network membership alone never proves volume isolation.

Create and start dispatches receive the operation's `AbortSignal`. If cancellation races a successful create, the returned exact identity is inspected and durably recorded before cancellation is honored. The container is not started and no next mutation is dispatched. Cancellation at network/volume/init/runtime creation boundaries retains ownership evidence for later review; it does not fabricate cleanup or automatically adopt a partial source.

PG preparation uses the fixed official entrypoint root-init shape, health convergence, graceful stop/join and exact removal before the numeric 70:70 runtime. A separate still-unenrolled materialization boundary must verify PG-owned TLS/SCRAM configuration inside the owned PG volume and numeric ownership for MinIO/Valkey volumes. A developer-owned 0600 host key is not made broadly readable to PG. Final health contracts require authenticated certificate-bound TLS `SELECT 1`, S3 `LIST_BUCKETS` and Valkey `PING`, plus plaintext and unauthenticated rejection. These are interface contracts and fake-Docker developer tests until their real providers and live evidence exist.

Remaining subpackets must supply exclusive retained secrets/one CA/cert generation and verification; exact volume materialization and a direct source Docker executor; real authenticated probes; real current migration/ledger operations; valid representative fixtures including the three-page PDF; object seed/seal; production-validator-backed five-role signed capsule with distinct keys; transactional operation/backup reservation; container capture/package/encryption; and independent attempt/publication settlement receipts. Production/native recovery and all restore/application/promotion/rollback gates remain unchanged.
