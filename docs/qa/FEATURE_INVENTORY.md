This inventory is the working source for phased feature discovery and regression coverage planning across the DARSHAN product suite.

Current QA entrypoint: `docs/qa/README.md`. Full-product scenario coverage is in `docs/qa/FULL_PRODUCT_QA_MATRIX.md`; runtime-only evidence requirements are in `docs/qa/RUNTIME_EVIDENCE_QA_CHECKLIST.md`.

## Evidence Rules

- Code is the source of truth. Existing markdown docs may be used as hints only and must not be treated as confirmation by themselves.
- A row may be marked `confirmed-by-code` only when at least one evidence column points to a verified repo path in source, config, schema, manifest, or test assets.
- Use `needs-runtime-verification` when the implementation path exists but the result depends on target runtime evidence.
- Use `historical/stale` when a row or note is preserved from prior QA history and must not be treated as current proof without rechecking code.
- Use `deferred-gap` when a row is a planned QA bucket, robustness backlog, or known gap rather than an implemented feature.
- Leave individual evidence cells blank rather than guessing.
- Evidence columns are cross-repo:
  - `Route`: CMS route or backend API route/module
  - `Component`: CMS page/component or player UI/preload entry when relevant
  - `Service`: backend service/repository or player service/module
  - `Schema`: DB table/schema anchor or deployment manifest asset when applicable
  - `Test`: existing unit, integration, e2e, fault, performance, or rules test

## Status Vocabulary

| Status | Meaning |
| --- | --- |
| `confirmed-by-code` | Verified directly in source, schema, manifest, or test files. |
| `needs-runtime-verification` | Implementation path is code-backed, but target browser/device/deployment evidence is still required. |
| `historical/stale` | Preserved prior QA evidence or note; recheck code before using it as current proof. |
| `deferred-gap` | Known QA gap or robustness bucket that is not a current implemented feature claim. |
| `inferred-needs-verification` | Legacy status retained for historical rows only; prefer `needs-runtime-verification` or `deferred-gap` for new rows. |

## Canonical ID Formats

- Phase inventory IDs use `PH{N}-{DOMAIN}-{NNN}`.
- Detailed appendix IDs use stable layer-local prefixes such as `CMS-001`, `BE-001`, `PL-001`, and `INT-001`.
- Example phase ID: `PH2-SCHED-004`.
- Appendix IDs do not replace phase IDs; they provide page-, workflow-, and cross-layer traceability underneath the phase taxonomy.
- `DOMAIN` is a short capability family label and does not need to map 1:1 to a repo name.
