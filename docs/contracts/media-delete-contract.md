# Recoverable Media Delete Contract

`DELETE /api/v1/media/:id` checks current permissions, ownership, and usage before setting `deleted_at` and `deleted_by`. It preserves the prior processing status, source/ready/thumbnail pointers, storage-object rows, and object bytes. A repeated delete by an authorized caller succeeds with `already_deleted: true`. `?hard=true` returns `400 MEDIA_HARD_DELETE_DISABLED`.

An in-use item returns `409 MEDIA_IN_USE` with `details.references`. A non-owner without management authority receives `403 MEDIA_DELETE_FORBIDDEN_OWNER`; authorization precedes any content disclosure. Deleted items disappear from the ordinary Media list, detail, authoring selection, new media URL issuance, and processing jobs. URLs issued before deletion cannot be revoked retroactively; their short expiry still applies.

Deletion and new Media associations are serialized on the referenced Media row. Chat attachments/bookmarks, presentation items, current Screen media, Emergency media and default/branding settings must lock and revalidate an active row before writing. If an association commits first, deletion returns `MEDIA_IN_USE`; if deletion commits first, the racing authoring write returns a conflict and creates no association. PoP remains historical evidence: an event committed first blocks deletion under the existing usage policy, while an already-completed late event may still be recorded after deletion.

`GET /api/v1/media/deleted?page=N` lists deleted items in pages of 100, starting at page 1 with IDs, original ownership, type, status and deletion metadata. `POST /api/v1/media/:id/restore` returns `{ id, already_restored }`. Both require a current ADMIN or SUPER_ADMIN role and effective `manage Media` permission. Restore retains the original ID and ownership, verifies referenced storage rows and object existence, and returns `409 MEDIA_RESTORE_OBJECT_MISSING` when a required object is unavailable. The list, delete and restore operations are audit logged. Old deletions that already removed objects cannot be restored by this contract.

The CMS Media Library presents one recoverable Delete action and an administrator-only Deleted Media list with Restore buttons. The API remains authoritative for stale UI state. Backup and restore of deleted records must include PostgreSQL rows and retained MinIO bytes.
