# User management authorization (Packet 1)

For a conditional `update User` grant, authorization must match both the stored account and its proposed post-PATCH state. A grant limited to `first_name: "Allowed"` cannot rename an otherwise eligible OPERATOR outside that condition; a denied update leaves the account and sessions unchanged.

Account mutations commit database session revocation before publishing realtime invalidation. A publisher outage or unexpected publish exception is logged after local socket disconnection; it does not turn an already-committed account change into an HTTP failure. REST and protected socket checks still use the revoked session table. Remote idle-socket delivery during a bus outage remains a live-test gate.

Session refresh must update an existing session row; if that row was removed after initial token verification, the request returns `401` and emits no refreshed access token. Authenticated logout revokes the session and sends clearing access/CSRF cookies with `Max-Age=0`; the response refresh hook must not overwrite those clearing cookies or send an `x-access-token` header.

Account management uses the authenticated actor's effective grants, including inherited grants. A grant with unresolved `$user` conditions is ignored. Only an unconditional effective `manage User` or `manage all` grants global account management. This permission does not grant access to role-definition APIs.

Every authenticated request requires a live session and an active, non-deleted account. The signed token's role ID, role name and department must still match the stored account/role; a mismatch is rejected as revoked even if a session row remains. Ownership-sensitive mutations repeat this comparison against the locked account and role inside the write transaction before changing content. Account and role changes also delete affected sessions transactionally, so these claim checks are a second fail-closed boundary, not a replacement for revocation.

Without global User management, an actor may create, update, reset, disable or delete an account only when the action is explicitly granted, the target account belongs to the actor's department, and its actual stored role is the built-in `OPERATOR`. The same check applies to both the existing and proposed account role and department. A manager with no department has no assignable account target. The server rechecks these conditions and the actor's current session inside the write transaction.

On `PATCH /api/v1/users/:id`, `department_id: null` explicitly unassigns a department for a global User manager. Omitting `department_id` leaves it unchanged. Both CMS Users and Operators edit forms send `null` for their "None" choice. A scoped manager cannot unassign an account because the proposed target would leave their department. A supplied department UUID on create, invite or update must resolve to an existing Department in the write transaction; an authorized request naming a missing Department returns `404` without creating or changing an account. Those account writes hold a shared lock on the Department until commit. Department deletion revalidates the caller's current session and effective permission, checks a conditional grant against the locked Department record, then counts user/content usage and deletes in the same transaction. Supported API writes and deletion therefore have one commit order. Migration `0048_user_department_foreign_key.sql` adds the database-level `users.department_id -> departments.id` constraint with `ON DELETE RESTRICT` and a supporting index, so direct database/import writers cannot bypass referential integrity. `NULL` remains the supported unassigned state. The migration locks both tables and fails before schema mutation with an orphan count and sample user IDs if legacy invalid references exist; operators must repair those rows explicitly and rerun it. The API race and migration rehearsal tests are authored but still require execution on disposable PostgreSQL.

Department API create/update also revalidate the current actor inside the write transaction and evaluate record conditions against proposed create fields or both stored and proposed update fields. List/detail enforce read grants on actual Department records; supported equality conditions on `id`, `name`, and `description` filter SQL rows and totals before pagination, while unsupported/malformed read conditions fail closed. A conditional grant does not expose an unrelated Department. The CMS hides mutation controls for nonmatching records, disables a form when its proposed value leaves the grant, scopes Department/operator query keys to the signed-in user, and clears open forms on account change. Without User read it does not fetch or display operator identities. These paths are source/build/unit checked, but their PostgreSQL and browser route matrices are authored and not yet executed.

Non-global ordinary people directories return only active, sign-in-eligible, non-deleted same-department users, or the eligible actor alone when no department is assigned. A PENDING, expired, or malformed invitation is therefore absent from Users/Operators detail and chat-participant selection even though its storage-level `is_active` value is true. Client filters only narrow this scope, and `is_active=false` returns an empty result and total zero for non-global actors. The invitation endpoint is the deliberate exception: permitted same-department managers can see pending/expired invitation records there without receiving their token. Global User managers may see disabled or pending non-deleted accounts for administration. Before/after invitation filters cast `ext.invited_at` only when it matches the exact Gregorian UTC format written by the app; malformed legacy values safely fall back to `created_at` rather than failing the whole directory request.

User DELETE is idempotent for an authorized global User manager: a repeat call on the same tombstone returns `200` with `already_deleted: true`, no second deletion audit, and no second session broadcast. Scoped managers cannot discover a tombstone through a repeat direct DELETE and receive `404`, matching their non-global directory boundary. The database-backed route regression for both actors is authored but has not been rerun on the current P01 build.

Directory record conditions are supported for canonical lowercase UUID `id`, `department_id`, and `role_id` fields. Missing, malformed, or unsupported conditions are ignored as grants; they never widen a list or produce an invalid UUID database query.

Invite-list status filters accept `pending`, `expired`, and `activated`; legacy `active` and `approved` values map to `activated`. Unknown or empty comma-separated values return `400 BAD_REQUEST` rather than silently removing a requested filter.

Login `user` and `GET /api/v1/auth/me` include:

```json
"authorization": {
  "rules": [{ "action": "read", "subject": "User", "conditions": { "department_id": "resolved-id" } }],
  "is_global_user_manager": false
}
```

The rules represent only the authenticated actor. User list/detail items include `permissions.can_update`, `permissions.can_delete`, and `permissions.can_reset_password`. Clients should use these flags for existing-account controls. The CMS Users and Operators edit forms keep unsaved fields through an unchanged list refresh, but close when the refreshed record's `updated_at` changes or its `can_update` flag is withdrawn. Direct User, Invitation and Operator create forms evaluate `create User` against their proposed email/role/department; edit forms require `update User` to match both the stored account and proposed result. A mismatching proposal disables submission and each submit handler repeats that guard, while the server remains the final authority. `GET /api/v1/users/management-options` returns candidate `{id,name}` roles and departments; a global User manager needs no Role or Department read grant to call it. Global managers may deliberately select no department, but every nonempty selection on all three form surfaces must still exist in the latest options response so a removed or forged Department fails closed in both the button and handler. Scoped managers receive only the canonical OPERATOR role when it is marked `is_system=true`, plus their own department; a departmentless non-global manager receives empty choices. Candidate options do not themselves authorize an account mutation.

CMS Users, Operators and invitation-list caches include the authenticated user ID in their query keys. Login/logout clears cached queries and changes the API request generation; a late result from the previous identity must not populate the next account's directory. Storage events and `BroadcastChannel` provide the immediate cross-tab signal. As a fail-closed fallback when both are blocked, the authorization query always revalidates `/auth/me` when the old tab regains focus; a returned user ID different from the locally rendered account is never used for permissions and clears Redux, query, session-storage and realtime state through the same central cleanup path. The identity/focus units and browser scenario are source-authored, but the two-tab cases have not yet executed against a running CMS/API.

Built-in role definitions (`SUPER_ADMIN`, `ADMIN`, `DEPARTMENT`, `OPERATOR`) are read-only. An authorized update/delete receives `409 SYSTEM_ROLE_IMMUTABLE`; an unauthorized caller receives `403`. Custom-role create/rename to a trimmed, case-insensitive built-in name receives `409 RESERVED_ROLE_NAME`. The ability builder applies built-in SUPER_ADMIN authority and the ADMIN branding restriction only when the stored role also has `is_system=true`; a non-system name alone is not sufficient. Legitimate custom-role edits revoke direct and inherited users' sessions. Account changes revoke target sessions in the committing transaction and publish invalidation after commit. Outbound authenticated socket events also recheck the shared session table before delivery.

Startup repairs permission drift only for exact-name roles already marked `is_system=true`, and revokes direct and transitive inheritors' sessions in its transaction before accepting requests. If an exact built-in name has `is_system=false`, or a reserved case/space variant exists with either marker value, startup stops with `SYSTEM_ROLE_IDENTITY_CONFLICT` for administrator review; it does not promote, rename, or accept the role. Development/demo seed performs the same preflight. Production bootstrap, adoption, and bootstrap inspection return a conflict for the same noncanonical identities; fresh bootstrap inserts built-ins only into an empty application database and does not use a conflict-upsert to promote roles. After verifying provenance, an administrator must repair the database explicitly before restarting. Startup repair and custom-role updates delete affected sessions through a database subquery, rather than expanding every affected user ID into SQL bind parameters. The affected IDs are still collected for post-commit notification. Session invalidation broadcasts are split to fit the configured realtime payload limit, including when a role repair affects many accounts; local sockets disconnect first. If a broadcast fails, publishing stops after that batch and logs incomplete delivery rather than waiting on every remaining batch. When Valkey is unavailable, the shared session table remains authoritative for REST, protected socket actions and outbound pushes. A database-backed drift/unchanged-role regression has been authored but not run; physical two-node delivery and failure behavior remain developer-runtime gates.

The canonical-name collision preflight uses the same trimmed, case-insensitive reserved-name comparison as custom-role creation. A legacy non-system role named, for example, ` admin ` also stops startup, seed, bootstrap, adoption and recovery for review; it is not silently promoted.

The administrator recovery CLI exposes `roleIsSystem` on inspection and refuses create, recover, or deactivate when an exact built-in name has `is_system=false` or any reserved case/space variant exists. Its `--grant-super-admin` path never assigns a role solely because its normalized name or marker looks privileged. A rejected maintenance operation leaves account, session, and audit rows unchanged. These source/build checks have authored but unexecuted PostgreSQL regressions; recovery remains an operator-controlled, offline procedure.

Role create authorization evaluates conditional `Role` grants against the proposed record; detail/delete evaluate the stored record. Update must authorize both the stored record and its proposed post-update state, so a name-limited editor cannot rename a role outside the permitted name. The list and permission-metadata endpoints expose subject-wide catalogues, so they require an unconditional effective `read Role`; a record-limited grant cannot open either catalogue. The ADMIN branding exception likewise defaults to denied and re-allows only explicit unconditional BrandingSettings actions. An invalid or record-conditional branding grant cannot silently lift that subject-wide restriction.

API-key and webhook management also evaluates custom-role grants against records rather than display names or subject-only checks. Supported list conditions are equality on `id`, `name`, and `created_by`; webhook reads additionally support `target_url`. Unsupported fields and malformed UUIDs produce no list rows, and filtering occurs in SQL before API-key pagination/counting. Create checks proposed fields, update checks both stored and proposed webhook state, and rotate/revoke/delete/test checks the locked stored record after current-session reauthorization. API-key hashes are never serialized. Webhook signing secrets and configured headers are absent from lists and mutation responses; a newly created webhook secret and newly created/rotated API-key secret are returned once with `Cache-Control: no-store`. The CMS keeps those one-time values only in page state, clears them on dismissal/account change, and never stores a newly issued API key in Redux or browser session storage. A mocked browser scenario for conditional row controls and one-time-secret handling is authored and Playwright-discoverable, but neither it nor the conditional PostgreSQL route matrix has run under the live resource gate.

The CMS role editor evaluates update/delete grants against each returned Role record before enabling its controls. Update checks both the selected record and the edited draft before enabling Save and again on submission; Create checks its proposed fields. A blank description is sent as an empty string accepted by the API, not `null`. These UI checks do not replace the server's transaction-time authorization. The record-limited CMS browser scenario is authored but has not yet been run against the application.

Organization and branding settings are singleton/collection APIs with no individual record to evaluate a condition against. Reads and updates therefore require an unconditional effective `OrgSettings` or `BrandingSettings` grant, respectively. `GET /api/v1/settings` omits the `org.branding` entry unless the actor also has unconditional `read BrandingSettings`. `POST /api/v1/settings` routes the `org.branding` key through `update BrandingSettings`, so the generic endpoint cannot bypass the dedicated branding permission. The CMS authorization helper also treats conditional grants on these settings subjects as insufficient. Database-backed API assertions for this contract are authored, but have not yet been executed.

SSO configuration is also treated as an organization-wide security setting: list requires unconditional effective `read SsoConfig`, while upsert and deactivate require unconditional effective `update SsoConfig` (including inherited `manage`). A record-conditional SSO grant does not open the full active-config list or change the active provider, even if its condition names an existing config ID. The CMS route guard applies the same subject-wide check; a read-only actor can view but cannot edit the form or use Save/Disconnect. The API and browser regressions for this boundary are authored but have not yet run against the application.

`POST /api/v1/users/activate` accepts only a current, unexpired pending token for an already-active invited account. It cannot reactivate an administrator-disabled account. The account and token are rechecked under a row lock before consuming the token.

The activation POST is public and does not rely on an existing login cookie or CSRF cookie. Its exact route is exempt from cookie-CSRF checks; the unguessable invitation token and password-strength policy remain mandatory. The invite creation and other authenticated account writes keep their normal CSRF protection. The route test is authored but has not run under the live PostgreSQL gate.

The CMS has a public `/activate#token=<code>` page that calls the activation API, displays validation/expiry errors and returns the invitee to sign-in after success. The token remains in the URL fragment rather than the HTTP request path/query, and successful navigation replaces that history entry. The user chose manager-mediated delivery: invite creation displays a copyable link once, explicitly says no email is sent and does not put the token in invitation lists. Invite creation returns no temporary password; the database-required password hash is made from a high-entropy unreturned placeholder. The link is cleared from the CMS view and mutation state when dismissed or the manager identity/permission changes. The manager must share it through an approved secure channel. If the link is lost or expired, a permitted manager can confirm **Replace link** on an awaiting-activation invitation. `POST /api/v1/users/invite/:id/replace` requires the list record's `expected_updated_at`, rechecks the current actor's session, `create User` grant and target scope in a transaction, locks the pending account, rotates its token and seven-day expiry, resets even a legacy stored `EXPIRED` status to `PENDING`, revokes old sessions, and records one `USER_INVITE_LINK_REPLACED` audit event without the token; the old link becomes invalid immediately. A competing request based on the same version receives `409 INVITATION_CHANGED`, so two managers are not both handed apparently-current links. The list exposes `can_replace` and `updated_at` but not either token, including for expired pending invitations. Invite-create, replacement and generated-password reset responses containing one-time credentials set `Cache-Control: no-store`; only reset-password returns a generated password. Activated, disabled and deleted accounts cannot receive a replacement; a scoped manager's direct request for an inactive hidden target returns not-found. Mocked manager/invitee browser and PostgreSQL route regressions are authored but not yet executed.

An invited account is database-active so the token activation route can use it, but it is **not sign-in eligible** until invitation status is `ACTIVATED` and the token is cleared. Password login returns `403 FORBIDDEN` with an activation prompt for a pending invite even when a test fixture knows the stored pre-activation password; production managers and invitees are never given the high-entropy placeholder. Expired and inconsistent invite metadata are likewise denied. Session verification and transaction-time mutation authorization reject a pending invitee's legacy session from an older build. Activation changes the password, consumes the token and revokes any existing sessions in the same database transaction; afterward the invitee signs in only with the chosen new password. A direct-created account with no invite metadata remains eligible. The pure-state unit tests and backend build pass; the authored API/DB lifecycle regression still needs a disposable PostgreSQL run.

Invitation filtering never casts untrusted legacy JSON directly to a database timestamp. Listing and activation share a 32-hex-character token contract and the same exact `Date#toISOString()` UTC expiry contract. A pending invitation with a blank/malformed token or a missing/noncanonical expiry is treated as `EXPIRED`: it cannot activate or authenticate, appears in the authorized manager's expired list without exposing its stored token, and can receive a replacement link. If corrupt or legacy data gives the same canonical token to more than one non-deleted invitation, public activation fails closed as not found and changes neither account; a permitted manager must replace the affected invitation link by its authorized record ID. The database-backed route assertions for these recovery paths are authored but still require the disposable PostgreSQL run.

Last-active-SUPER_ADMIN protection counts only active, non-deleted and sign-in-eligible accounts assigned to the exact `is_system=true` SUPER_ADMIN role. A PENDING/expired invited SUPER_ADMIN is not a valid survivor even though its database `is_active` value is true, and a false-marker/custom row named SUPER_ADMIN is neither a survivor nor a protected built-in. The account/role concurrency, identity-drift and pending-invite regressions are authored but have not yet run against PostgreSQL.

Production bootstrap adoption and inspection likewise refuse a pending invited or deleted administrator as their usable SUPER_ADMIN authority. Fresh bootstrap creates a direct account without invite metadata. The adoption/inspection database regression is authored but remains unexecuted.

The shared condition resolver also affects content, scheduling and chat. Schedule Request detail checks the stored request record; list rows, pagination totals and status summary apply the same record predicate before returning data. The list predicate supports equality on canonical lowercase UUID `id`, `schedule_id` and `requested_by`, plus a valid request `status`. Unsupported Request condition fields fail closed in lists and counts. Schedule ownership remains a separate check.

For chat attachments, every selected Media record must first be readable under the same stored `owner_scope`/`owner_department_id` policy used by Media detail. A non-creator then needs a matching `update Media` grant for each record; built-in administrators satisfy this through their effective grants, not a role-name shortcut. A role limited to one Media ID cannot authorize a second attachment. Ownership is checked before READY state so an inaccessible PROCESSING file does not reveal its state through a readiness error. A file outside the sender's readable ownership scope remains forbidden even when its creator ID matches the sender. The database-backed route regression for this path is authored but has not yet run.

New Media/Layout/Presentation/Schedule ownership derives privileged scope from effective unconditional grants. The built-in SUPER_ADMIN retains restricted/private creation because its stored system-role ability includes unconditional `manage all`; the `SUPER_ADMIN` or `ADMIN` name alone cannot promote a new resource to a privileged scope.

The legacy `/api/v1/conversations` DM shim checks `read Conversation` against each actual chat conversation record for list, messages, send and read receipt operations. Starting a DM checks an existing record or the proposed DM fields before creation, then rechecks the actual record before membership upsert. Migration from an old `conversations` row has no stable chat-record ID before creation, so only an unconditional read grant may trigger that legacy migration; a conditional grant can access matching DMs already present in `chat_conversations`. These paths still require database-backed route regression before P01 sign-off.
